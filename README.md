

```
          +-------------------+
          |       main        | ← 穩定版，正式釋出
          +-------------------+
                   ↑
                   │ (合併 release 完成後)
          +-------------------+
          |     release/x.y   | ← Sprint 結束時建立，最後測試 & QA
          +-------------------+
                   ↑
                   │ (Sprint 內完成的功能)
          +-------------------+
          |      develop      | ← 持續整合，所有 feat 都先進來
          +-------------------+
             ↑        ↑
             │        │
   +----------------+ +----------------+
   |   feat/0415    | |   feat/0420    | ← 從 dev 開出來的功能分支
   +----------------+ +----------------+

   +-------------------+
   |     hotfix/XXX    | ← 緊急修正，直接從 main 開出
   +-------------------+

```

**feat/XXX**：

- 從 `develop` 開出來，完成後合併回 `develop`。

**develop**：

- Sprint 期間的整合分支。

**release/x.y**：

- Sprint 結束時，從 `develop` 建立。
- 做最後測試、修正 bug，確認穩定後再合併到 `main`。
- 好處：避免 `develop` 的不穩定直接影響 `main`。

**main**：

- 永遠保持穩定，只接受 release 分支合併。
- 代表正式版本。
- 如果 main 緊急需要修 bug，要有明確的 hotfix 流程，避免直接在 develop 修，導致 main 沒有同步。

**hotfix/XXX**：

- 如果 `main` 緊急需要修正，直接從 `main` 開出。
- 修完後合併回 `main` 和 `develop`，保持一致。

----

```
如果 develop rebase 時發現有 bug 帶回自己的 feature 分支時: 

- **確認 bug 責任歸屬**
    - 先判斷這個 bug 是誰的 commit 引入的。
    - 如果你能修，就直接在自己的 feature 分支修掉，並且通知原作者他們的分支有問題，避免他們繼續基於錯誤的 develop 開發。
- **修正策略**
    - **你能修**：在自己的 feat 分支修正，然後合回 develop，確保大家 rebase 時不會再被污染。
    - **你不能修**：暫時停下來，等原作者修好並合回 develop，再 rebase 你的分支，確保乾淨。
- **通知團隊**
    - 修正完成後，要通知所有開發人員：develop 已經修好，可以安全 rebase。
    - 這樣避免大家在 bug 還存在時 rebase，造成更多污染。
```
